# Planner 운영

필수 Gate·권한·상태 경계는 [SKILL.md](../SKILL.md#planner-gate), 역할은 [office-planner.toml](../roles/office-planner.toml)이 원본이다. Main은 항상 Planner 관점의 요구사항 정의·직접 질문과 배정·구현 통합·최종 결과를 책임진다. 별도 Planner는 복잡한 요구사항 분석을 분리할 이득이 있을 때 선택하는 위임 역할이다. Explorer는 현재 구현의 사실을 조사하고 Specialist는 제한된 전문 자문을 제공한다. Planner가 기술 사실을 추측하거나 구현·리뷰·QA를 대체하지 않는다.

## 검토와 질문

목표, 범위, 성공·완료 기준, 우선순위, 중요한 제약, 기존 구조 변경 허용 범위, 결과물 형태, 사용자가 중요하게 보는 기준, 구현 대안, 잘못 추론하면 큰 재작업이 필요한 사항을 검토한다. 모두 질문할 필요는 없으며 이미 확정된 내용은 다시 묻지 않는다. 자료·기존 코드·프로젝트 규칙으로 확인할 사실은 먼저 조사한다.

내부적으로 “지금 확인하지 않으면 도중에 다시 물을 가능성이 높은가?”, “임의 판단하면 결과를 보고 재작업을 요청할 가능성이 높은가?”를 확인한다. 어느 쪽이든 해당하고 결과에 중요한 영향이 있으면 구현 전에 질문한다. 방향·구조·작업량·사용자 취향·되돌리기 어려운 선택은 사용자 결정이며, 작은 네이밍·사소한 스타일·일반 기본값·쉽게 바꿀 세부사항은 Main 또는 위임한 Planner가 판단한다.

질문은 일반적으로 2~4개 선택지와 추천 이유를 제시한다. 가능한 경우 보수적·균형적·적극적 대안을 포함하되 억지로 선택지를 만들지 않는다. `1A 2B`처럼 짧게 답할 수 있게 번호를 붙인다. runtime 질문 도구가 2~3개 등 더 좁은 제한을 두면 해당 제한에 맞춘다. 자유서술은 선택지로 의미를 담기 어려운 경우에 쓴다. 답에 따라 다음 질문이 달라지면 목표 → 범위 → 구현 방향 순서처럼 단계적으로 확인한다.

“알아서 해”에도 중요한 미결정이 있으면 “나머지는 제가 판단할 수 있지만, 아래 항목은 결과 차이가 커서 확인이 필요합니다”라고 이유를 설명한다. 추천은 선택을 대신하지 않는다. 사용자가 명시적으로 위임한 결정 범위는 보존하되 포괄적인 위임만으로 중대한 미결정을 확정하지 않는다.

예: “로그 화면 개선해줘”에는 먼저 불편한 점을 `A. 검색 (추천: 현재 확인된 불편 근거가 있을 때) / B. 가독성 / C. 실시간 확인 / D. 현재 상태 분석 후 추천`으로 묻는다. 목표 응답 후 변경 범위를 `A. UI 최소 수정 / B. UI와 상태·컴포넌트 변경 / C. 기능 구조 변경`처럼 확인하고 추천 이유를 실제 근거로 설명한다. 조사 후 새로운 중요한 결정이 생기면 Main이 직접 다음 질문을 하며 위임한 Planner는 질문안을 반환한다.

## Main 전달

Main이 직접 수행할 때는 중요한 미결정에 대해 NEED_INFO로 질문하고, 해소되면 READY로 사용자에게 쉬운 요약을 제시한 뒤 내부 실행 명세를 정리한다. 명확한 요청은 PLANNER_PASS로 바로 진행한다. 아래 child 인계 양식을 매번 사용자에게 출력할 필요는 없다. 다음 형식은 별도 Planner에 분석을 위임한 경우에 사용한다.

Planner는 공통 Agent 결과 보고의 수행 결과 안에 아래 판단을 담아 Main에 반환하고 task를 끝낸다. Main은 지원되는 질문 도구 또는 채팅으로 질문을 중계한다. 도구 이름·인자·사용 가능 모드를 가정하지 않는다. Main이 받은 응답과 기존 확정 명세를 다음 Planner task에 전달한다. 사용자 응답이 없으면 의존 구현은 계속 보류하며 독립 조사·작업만 진행한다.

- `NEED_INFO`: `[PLANNER_RESULT]`, `Status: NEED_INFO`, 확인된 사실·결정, 남은 중요한 질문·추천 이유, 보류할 의존 작업과 진행 가능한 독립 작업을 담는다.
- `PLANNER_PASS`: `[PLANNER_RESULT]`, `Status: PLANNER_PASS`, 추가 확인이 필요 없는 근거와 적용할 요청·범위·완료 기준을 짧게 담는다. Main이 직접 Gate를 통과시킬 때도 같은 판단 근거를 보존하되 별도 문서 생성을 강제하지 않는다.
- `READY`: 먼저 목표·우선순위·범위·구현 정책·완료 조건을 사용자가 이해할 수 있는 말로 요약하고 다음 실행 명세를 전달한다. 중대한 미결정이 있으면 READY로 표시하지 않는다. 질문 답변만 확보하고 요약·명세 없이 구현 담당자에게 넘기지 않는다.

```text
[PLANNER_RESULT]

Status: READY

Goal:
- ...

Scope:
- ...

Priority:
1. ...
2. ...

Constraints:
- ...

User Decisions:
- 사용자 답변과 명시적으로 확정한 조건

Planner Decisions:
- 작은 네이밍·가역적인 세부 기본값과 근거

Out of Scope:
- ...

Completion Criteria:
- 검증할 수 있는 완료 기준

Recommended Execution:
- 필요한 조사·구현·리뷰·검증과 의존 순서
```

Main과 다른 담당자는 사용자 확정 요구사항을 임의 변경하지 않는다. 기존 요구 충돌, 예상 밖 기술 제약, 결과 차이가 큰 대안, 범위 급증, 완료 기준을 위한 새 결정, 중요한 사용자 의도 추론이 생기면 Main이 기존 명세·새 근거·영향·선택지로 사용자에게 재확인한다. 복잡한 분석을 분리할 때는 해당 자료를 Planner에 전달할 수 있다. 작은 가역적 구현 선택까지 재질문하지 않는다. Main 또는 위임한 Planner는 새 중요 결정만 확인하고 명세를 갱신한다. READY와 PLANNER_PASS는 Plan Mode 실행 승인이나 프로젝트 필수 검사를 대체하지 않는다.

## 시나리오 점검

아래는 지침 적용 기대 결과이며 live runtime 실행 성공을 뜻하지 않는다.

| 요청·상황 | Gate 판단과 기대 동작 |
|---|---|
| “대시보드 좀 개선해” | NEED_INFO. Main이 별도 Planner 없이 목표·불편 근거부터 쉬운 선택 질문을 직접 제시. 사실 조사는 가능하며 방향에 의존하는 UI 수정은 보류 |
| 여러 영역의 요구 충돌·대안 분석이 복잡함 | Main이 필요하면 Planner에 분석 위임. Planner는 NEED_INFO 질문안 또는 READY 명세 반환, Main이 사용자 소통·결정과 통합 유지 |
| 정확한 파일의 “완료됌”을 “완료됨”으로 수정 | Main이 PLANNER_PASS. Planner 생성·추가 질문 없이 최소 수정과 필요한 확인 |
| “알아서 해”, 데이터 보존 정책 미결 | NEED_INFO. 보존·삭제처럼 되돌리기 어려운 선택은 사용자 확인. 일반 기본값·네이밍만 Main 자체 판단 |
| READY 후 기존 API로 완료 기준을 만족할 수 없는 기술 제약 발견 | Main이 영향과 대안으로 새 중요 결정만 직접 재질문. 해당 API 의존 구현은 보류하고 독립 작업 계속 |
| 질문 뒤 사용자 응답 대기 | Main이 직접 질문한 뒤 의존 구현 보류. 별도 Planner가 배정된 경우 질문 반환 후 종료하고 Main이 중계. 시간 경과·추천을 동의로 보지 않음 |
| Plan Mode에서 READY 확보 | 읽기 조사·업무 계획서까지만 진행. READY를 실행 승인으로 보지 않고 코드 수정·구현 agent 시작·commit·push 보류 |
